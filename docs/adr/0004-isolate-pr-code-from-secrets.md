# ADR 0004: Isolate PR code from secrets

For reviewers and future maintainers: why PR code never runs next to the model key, and why agent config comes from the base branch.

## Context

PR code is untrusted. Its npm install scripts, Vitest config and test files all run when tests run. On a host that holds the model key, that code could read the key and send it out.

A same-repo PR can edit any workflow file it runs with. A `pull_request` workflow reads the file from the PR head, so a PR could drop the guard steps, read the repo's secrets, or post a green status itself.

PR text (title, body), and the agent summaries it can steer, are untrusted too. The agents treat it as data, and the report renders it in a safe form.

Fork PRs come from people outside the repo. They must not reach any secret.

## Decision

1. **Two workflows.** `pr-intake` runs from the PR on `pull_request`. It has no secrets, no token scopes, no budget variables and no PR code; it only uploads the `intake` artifact (PR number, head SHA, action, skip label). `pr-test-engineer` runs on `workflow_run` of `pr-intake`, or on a manual dispatch from `main`. GitHub runs it from the default branch, so a PR cannot edit it. Its `intake` job treats the artifact as untrusted data: `intake.ts` checks every field strictly, then reads the live PR and stops, with no status and no comment, unless the PR is open, from this repo, and still at the head the run was for. Every value from the event or the artifact reaches a shell only through `env:`.
2. **Environment.** The model secret and the GitHub App's private key live in the Environment `test-agent`, whose deployment branches are limited to `main`, and no repo-level copy exists. Only jobs of `pr-test-engineer` use the Environment: `agents` (model key), and `scope`, `bot_commit` and `publish` (App key). An edited `pr-intake` runs on the PR's merge ref and cannot enter it.
3. **Privilege split.** A job that holds a write token or the model key never runs PR code on the host. `agents` holds the model key and a read-only token, and runs PR code only inside containers. `scope`, `bot_commit` and `publish` hold a token of the GitHub App (see decision 9) for their writes and a read-only `GITHUB_TOKEN`, run no model and no PR code, and use scripts from the base commit. `suites` runs PR code with a read-only token and no secrets.
4. **Base-branch config.** Before the agent runs, `agents` replaces the agent config and scripts with the base commit's versions: `.claude/`, `CLAUDE.md`, `AGENTS.md`, `.mcp.json` and `.github/scripts/`. It first removes every `.claude/`, `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md` in the tree, because nested instruction files load too. The logic is `.github/scripts/agent/overlay.sh`, read from the base commit, not from the checkout. The same script then checks the tree right before the Author and again before the Reviewer: it restores any of those paths that changed since the overlay, removes any instruction file that appeared, and warns with each file. Restoring is the defence; it does not fail the run, because the read-only sandbox and the write guard leave only the agent runtime itself able to write there. Code that ran in between (PR postinstall scripts, the Author's tests) therefore cannot steer an agent.
5. **Fork PRs get nothing.** `pr-intake` does not run for a fork PR, and `intake` stops for one (including a dispatch). The workflows never use `pull_request_target`, and `workflow_run` never checks out the PR head before `intake` has checked it.
6. **Container sandbox.** `.github/scripts/agent/sandbox.sh` runs npm tasks in a Docker container from a pinned image. The container gets no host environment, so the key is not inside. `install` has network access and no secret. `test` and `typecheck` run with no network. Dependencies live in Docker volumes, so the host's `node_modules` is not touched. The checkout is mounted read-only as a whole, so code in the container cannot change the hook script, the agent config, instruction files, git config or source. The only writable paths are the dependency volume, `backend/src/generated` during `install` (the Prisma client, git-ignored) and `<package>/coverage` during `test` (git-ignored; vitest reports go to `coverage/report`). The Author writes test files with its own tools on the host, never inside the container.
7. **Write guard, applied twice.** During the agent run, a PreToolUse hook refuses writes outside the test paths, and every shell command not listed in `AGENT_COMMANDS`, so the shell cannot write files either. Before the Bot commit, `bot_commit` checks the patch for non-test paths and symlinks. Both use the same rules in `.github/scripts/contracts/rules.ts`.
8. **PR text is data.** The agents are told not to follow instructions in it. The report sanitises agent text: it strips HTML, neutralises mentions and issue references, and removes links and images that point to other hosts.
9. **A GitHub App writes.** The pending and final status, the three PR comments and the Bot commit's push use an installation token of a GitHub App, made in the job by `actions/create-github-app-token` (pinned to a commit SHA) from the App's client ID (Environment variable `TEST_AGENT_APP_CLIENT_ID`) and key (Environment secret `TEST_AGENT_APP_PRIVATE_KEY`). Each job asks only for what it writes: `scope` statuses, `bot_commit` contents, `publish` statuses and pull requests. The token is limited to this repository. No job uses `GITHUB_TOKEN` to write. A job fails with the missing names, before it does any work, if the App is not set up: there is no fallback to `GITHUB_TOKEN`, because the ruleset accepts the status only from the App ([ADR 0005](0005-gate-merges-on-test-agent-verify.md)). The App's login is the repo variable `TEST_AGENT_BOT_LOGIN` (`<slug>[bot]`); each job checks that the key belongs to that login.
10. **The Bot's pushes start no run.** A push with an App token starts workflows, which a `GITHUB_TOKEN` push does not. `pr-intake` skips a run whose actor is the App's login (or `github-actions[bot]`), and the `intake` job of `pr-test-engineer` stops again on the actor and fails if `TEST_AGENT_BOT_LOGIN` is not set. Without that, a Bot commit would start a run, which could push another Bot commit.

## Consequences

- The model key is meant to stay out of every container, and PR code is meant never to run next to it. To check this, run a probe test through `sandbox.sh test backend`: it should see no `ANTHROPIC_API_KEY`, fail to fetch an external URL, and fail with `EROFS` when it writes anywhere in the checkout except `<package>/coverage`: `.git`, `.github`, `.claude`, `CLAUDE.md`, `backend/src`. A postinstall probe during `install` should likewise fail everywhere except `backend/src/generated`.
- Known gaps in the isolation are listed under limitations in [SOLUTION.md](../../SOLUTION.md). This ADR does not restate them.
- `suites` runs PR code on the runner host without secrets and without the Environment. The invariant allows this. The PR code can take the job's artifact token, so no job of `pr-test-engineer` uses a cache, no trusted step runs in `suites` after PR code, and `publish` trusts only artifacts whose producing job succeeded. What `suites` uploads (`reports`) is untrusted data.
- The PR is bound from the `workflow_run` event (`pull_requests[0]`, `head_sha`, `head_repository`), not from the artifact.
- Agent transcripts are not published, not even as an artifact, because they carry PR text and tool output. The `agents` log lists only the tool calls the permission rules denied.
- Fork PRs get no agent run and no status. A maintainer merges them by pushing the branch into the repo.
- A PR that changes `.claude/` or `.github/` cannot test its own agent config, because the run uses the base copy. See [ADR 0005](0005-gate-merges-on-test-agent-verify.md) for the skip label used on such PRs, and [ADR 0009](0009-test-agent-config-changes-against-committed-cases.md) for how such a change is tested before the merge.
- The workflow `pr-test-engineer` comes from the default branch, so a PR that changes it is not tested by its own run. That PR merges by the admin path in [ADR 0005](0005-gate-merges-on-test-agent-verify.md). The scripts it runs still come from the PR's base commit.
- The run starts about a minute after the push, because `pr-intake` runs first.
- A same-repo author can no longer make a green `test-agent/verify`. `pr-intake` is written with `permissions: {}`, but the PR can edit the file, so before the App it could ask for `statuses: write` and post the status as GitHub Actions, which was the status the ruleset accepted. The same held for any workflow on any branch with `statuses: write`. The ruleset now accepts the status only from the App ([ADR 0005](0005-gate-merges-on-test-agent-verify.md)); a workflow on a branch cannot read the App's key, because the Environment is limited to `main`. A status posted by `GITHUB_TOKEN` or by a person does not count. The limitation for `suites` is in [SOLUTION.md](../../SOLUTION.md).
- The App's private key is a long-lived secret. Anyone who can push to `main` (only an admin, through a PR) or who holds the key can post the status or push to any branch the App can reach. Rotate it from the App's settings page and run `scripts/setup-github.sh config`.
- The Bot commit is authored by the App (`<slug>[bot]`). Whether GitHub still asks to approve a workflow run for it is not known until the first Bot commit is pushed; either way the run does nothing.
- Comments that earlier runs posted as `github-actions[bot]` stay as they are; the App posts new ones, because `report.ts` updates only the comments of `TEST_AGENT_BOT_LOGIN`.
- Rollback: revert the PR that introduced the App, then run `scripts/setup-github.sh ruleset` from the reverted `main`, which sets the required status back to the GitHub Actions app (integration 15368). Do it in that order, or the status of the old workflow is not accepted.

## Status

Accepted.
